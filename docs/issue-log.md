## ISSUE-P-001(元 B1). 登録成功でダイアログが即閉じ、成功メッセージが見えない
- **発見日**: 2026-08-10(ユーザー報告「登録したとき画面が閉じてしまう。メッセージだけ出して閉じないでほしい」)
- **深刻度**: 中 / **対象**: `src/components/EstimateTool.tsx`
- **事象**: 過去見積を登録すると `<dialog>` が即 `close()` され、成功メッセージを確認できず、連続登録もできない。
- **原因**: `useEffect` で成功時に自動クローズしていた。
- **対応**: 自動クローズを廃止。`useTransition`+Server Action の手動制御にし、成功後も開いたまま `msg-ok` を表示。**新規登録のときだけ**再マウントキー(`newNonce`)を更新してフォームを初期化。閉じるのは「閉じる」ボタンのみ。
- **確認(当時)**: 2026-08-10 ブラウザ実操作で `dialogStillOpen=true`・メッセージ表示・フォーム初期化。
- **再確認(WO-003・2026-10-13)**: ✅ 登録成功後もダイアログが開いたまま成功メッセージが出て、フォームが初期化された([T-13](test-scenarios.md)・[15](screenshots/15-create-ok-form-reset.jpg))。
- **関連**: CHANGE-P-004

## ISSUE-P-003(元 B3). Vercel 初回デプロイのビルドが接続文字列の「クォート」で失敗
- **発見日**: 2026-08-11(Vercel 初回ビルドのログ)
- **深刻度**: 中(デプロイ不可。ローカルは正常に動くため気づきにくい=環境差の罠) / **対象**: Vercel 環境変数 `DATABASE_URL`・`.env.local` の記法・`src/db/index.ts`
- **事象**: ビルドが `neon()` で「not a valid URL」(`src/db/index.ts`)で失敗。ローカルの `dev`/`build` は正常。
- **原因**: `.env.local` が `DATABASE_URL="postgresql://…"` とダブルクォートで囲む記法。**ローカルの dotenv は囲みクォートを除去**するが、**Vercel の環境変数はクォートを値の一部として保持**するため、先頭が `"` の文字列が `neon()` に渡った。
- **対応**: Vercel 側の値から前後のダブルクォートを削除(`postgresql://` で始まり `sslmode=require` で終わる**裸のURL**)→ Redeploy で成功。秘密値はチャット・コミットに出さない。
- **確認(当時)**: Redeploy 成功。Vercel の完了画面に つもる のUI(全38件)が表示。
- **再発防止(適用済 2026-10-13・WO-003)**: `src/db/index.ts` で接続文字列の前後の空白・引用符(`"` `'`)を除去してから `neon()` に渡す。**運用ルールは [deploy-runbook.md](deploy-runbook.md) に明記**(裸URL必須)のまま。
- **再発防止の確認**: 型検査・lint・画面表示(ローカルは裸URLで通常動作)で確認。**クォート付きの値での起動確認はしていない**(Vercel 環境の再現は未実施。処理は正規表現による除去のみ)。
- **関連**: CHANGE-P-007

## ISSUE-P-005. 確定金額の記録が保存されない/未使用の列がある
- **発見日**: 2026-10-12 / **深刻度**: 中(PoC合格ラインの測定手段が機能しない) / **状態**: **対応済(2026-10-13・WO-003)** / **確度**: 画面で確認
- **事象**: 「確定金額を記録する」は `useState` の配列(`recHist`)に積むだけで、**DBに保存されない**。再読み込みで消える。叩き台との乖離・補正理由の蓄積(D34 が狙った「S3へ進む判断根拠」)ができなかった。
- **対応(スキーマ変更なし)**: 新しい Server Action `recordFinalAmount` を追加。引合い1回=**新しい行を1つ insert** する(既存行は触らない)。`status='draft'`・`source='tool'`・`amount`=確定金額・`draft_amount`=叩き台・`reason`=補正理由・引合い条件(種類/サイズ/用紙/色/数量/加工/データ状態/流用)・`cost=0`(**原価未入力を表す**。粗利計算には使わない)・`code=E-{id}`。`status='draft'` のため類似検索の母集団(reference/confirmed)と一覧には入らない。叩き台はクライアントの値を使わず**サーバーで条件から再計算**して保存する。詳細は [architecture.md](architecture.md) §2・§3。
- **確認**: T-08b ✅(再読み込み後も残る)。`searchMemos` が補正理由で記録行を引ける(「【つもる記録】」と確定額・叩き台を併記して表示)。件数「Neon 全38件」・一覧・類似検索の母集団には入らないことを画面で確認。スクショ [13](screenshots/13-record-saved.jpg)・[14](screenshots/14-record-after-reload-and-memo-search.jpg)。
- **残る課題**: 記録行(draft)を原価入力のうえ confirmed に昇格する機能は未実装(将来案: 昇格時は原価の入力を必須にする)。誤記録を消すため、記録欄に「削除」を追加した(確認つき。WO-003・計画外の小変更)。

## ISSUE-P-006. 登録が insert+update の2段で、非アトミック
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: 未対応(再現せず・**提案に留める**。スキーマ変更を伴うため WO-003 では直さない)
- **再現(WO-003・2026-10-13)**: 2段目だけを失敗させる手段が無く**再現していない**。通常の登録・記録は E-042 等で正常に採番された。事象は推測のまま。
- **事象(推測)**: `saveEstimate`(と `recordFinalAmount`)は `insert … returning id` のあと別クエリで `code` を update する。`neon-http` ではトランザクションを張っていないため、2段目だけ失敗すると行は作られ `code` が null のまま残る。
- **補足**: 試験で連番(id 41〜43)を消費した。連番は削除しても戻らないため、次の新規は E-044 になる(過去にも E-039 の欠番あり)。
- **案**: `code` を DB 側の生成列/トリガーにする、または1クエリで採番する(いずれもスキーマ変更=db-change)。

## ISSUE-P-007. DBエラーの文面をそのまま画面に返す
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: **対応済(2026-10-13・WO-003)**
- **再現(2026-10-13)**: 数量に int4 を超える値(99999999999)を入れると、旧コードは `parseInt` を通し、DB が失敗し、画面には drizzle の `Failed query: insert into "estimates" (…) values (…) params: …`(**SQL全文とパラメータ**)が出る。接続文字列は含まれなかった。
- **対応**: `saveEstimate`/`deleteEstimate`/`recordFinalAmount` の `catch` は画面に**固定文言**を返し、詳細は `console.error`(サーバーログ)へ。さらに int4 超過は事前検証で弾く。
- **確認**: 事前検証(`strictInt`)の動作を確認。DBエラー経路の画面確認は、事前検証が先に弾くため通常操作では再現できない(コード上の確認)。

## ISSUE-P-008. 存在しない id の更新・削除でも成功表示/数値入力が緩い
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: **対応済(2026-10-13・WO-003)**
- **再現(2026-10-13)**: ① 編集ダイアログを開いたまま別タブで同じ行を削除し、保存 → 旧コードは対象0件でも「更新しました」と返す想定(**旧コードでの画面再現は未実施**。対象0件でエラーにならないのは Postgres の仕様)。② `parseInt('12abc')`=12、`parseInt('1e3')`=1、`parseInt('99999999999')` は通る(JS の仕様どおり。ツールで確認)。
- **対応**: ① `update`/`delete` に `returning` を付け、0件なら「対象が見つかりません」を返す。② 数値は `src/lib/input.ts` の `strictInt`(数字のみ・int4 上限以内)で厳密にパース。id も同様。
- **確認**: ①は画面で確認(別タブで削除→保存→「更新できませんでした(対象が見つかりません…)」。[19](screenshots/19-update-missing-row-error.jpg))。②は `12abc`/`1e3`/`-5`/`99999999999` がいずれも NaN(=入力エラー)になることをスクリプトで確認。

## ISSUE-P-009. 語句検索で `%` `_` がワイルドカードとして効く
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: **対応済(2026-10-13・WO-003)**
- **再現(2026-10-13)**: `%` だけで検索する条件(`ILIKE '%%%'`)は、全件(読み取りで 23件が該当。画面では上限20件)に一致する。SQLインジェクションではない(パラメータ化されている)。
