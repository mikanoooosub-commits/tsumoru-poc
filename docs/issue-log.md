## ISSUE-P-001(元 B1). 登録成功でダイアログが即閉じ、成功メッセージが見えない
- **発見日**: 2026-08-10(ユーザー報告「登録したとき画面が閉じてしまう。メッセージだけ出して閉じないでほしい」)
- **深刻度**: 中 / **対象**: `src/components/EstimateTool.tsx`
- **事象**: 過去見積を登録すると `<dialog>` が即 `close()` され、成功メッセージを確認できず、連続登録もできない。
- **原因**: `useEffect` で成功時に自動クローズしていた。
- **対応**: 自動クローズを廃止。`useTransition`+Server Action の手動制御にし、成功後も開いたまま `msg-ok` を表示。**新規登録のときだけ**再マウントキー(`newNonce`)を更新してフォームを初期化。閉じるのは「閉じる」ボタンのみ。
- **確認(当時)**: 2026-08-10 ブラウザ実操作で `dialogStillOpen=true`・メッセージ表示・フォーム初期化。
- **本WOでの再確認**: ⏭️ 書込みを伴うため未実施(本番DB共有。[test-scenarios.md](test-scenarios.md) T-13)。コード上は `onSaveSubmit` が閉じずに `setSaveMsg` するのを確認。
- **関連**: CHANGE-P-004

## ISSUE-P-002(元 B2). 手動登録レコードの表示コード(code)が null になる
- **発見日**: 2026-08-10(ユーザー指摘)
- **深刻度**: 低(表示の不統一。機能に影響なし) / **対象**: `src/app/actions.ts`(`saveEstimate`)・`estimates.code`
- **事象**: 登録フォーム経由の見積は `code` が null で、一覧に `#38` と表示。シードの `E-001`〜`E-036` と体裁が揃わない。
- **原因**: insert で `code` をセットしていなかった(列が nullable)。
- **対応**: insert 後の id から `E-{id:3桁}` を自動付与。既存の null 2件(旧 `#37`/`#38`)は使い捨てスクリプトで E-037/E-038 に一度だけ埋め戻し。
- **確認(当時)**: 既存2件が統一され、新規登録が E-040 を自動付与(E-039 はテスト削除で欠番)。全38件でコード重複なし。
- **本WOでの確認**: ✅ 一覧に全38件が出て、E-037/E-038 が `E-` 形式で表示(T-05)。新規採番は ⏭️(書込み)。
- **関連**: CHANGE-P-005 / D39。→ 派生の懸念は ISSUE-P-006

## ISSUE-P-003(元 B3). Vercel 初回デプロイのビルドが接続文字列の「クォート」で失敗
- **発見日**: 2026-08-11(Vercel 初回ビルドのログ)
- **深刻度**: 中(デプロイ不可。ローカルは正常に動くため気づきにくい=環境差の罠) / **対象**: Vercel 環境変数 `DATABASE_URL`・`.env.local` の記法・`src/db/index.ts`
- **事象**: ビルドが `neon()` で「not a valid URL」(`src/db/index.ts`)で失敗。ローカルの `dev`/`build` は正常。
- **原因**: `.env.local` が `DATABASE_URL="postgresql://…"` とダブルクォートで囲む記法。**ローカルの dotenv は囲みクォートを除去**するが、**Vercel の環境変数はクォートを値の一部として保持**するため、先頭が `"` の文字列が `neon()` に渡った。
- **対応**: Vercel 側の値から前後のダブルクォートを削除(`postgresql://` で始まり `sslmode=require` で終わる**裸のURL**)→ Redeploy で成功。秘密値はチャット・コミットに出さない。
- **確認(当時)**: Redeploy 成功。Vercel の完了画面に つもる のUI(全38件)が表示。
- **再発防止案(未適用)**: `src/db/index.ts` で接続文字列の前後クォートを除去する防御を1行入れる。→ [change-log.md](change-log.md) の候補欄。**運用ルールは [deploy-runbook.md](deploy-runbook.md) に明記**(裸URL必須)。
- **関連**: CHANGE-P-007

## ISSUE-P-005. 確定金額の記録が保存されない/未使用の列がある
- **発見日**: 2026-10-12 / **深刻度**: 中(PoC合格ラインの測定手段が機能しない) / **状態**: 未対応(設計上の既知の制約) / **確度**: 画面で確認
- **事象**: 「確定金額を記録する」は `useState` の配列(`recHist`)に積むだけで、**DBに保存されない**。再読み込みで消える(画面にも「この画面内のみ」と表示)。叩き台との乖離・補正理由の蓄積(D34 が狙った「S3へ進む判断根拠」)ができない。
- **関連する未使用要素**: `estimates.draft_amount`・`reason` は書き込む画面が無い。`searchMemos` は `reason` を検索対象にしているが、中身が入る経路が無い(シードも未設定)。status の `draft`/`issued`、source の `tool` も未使用。

## ISSUE-P-006. 登録が insert+update の2段で、非アトミック
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: 未対応
- **事象(推測)**: `saveEstimate` は `insert … returning id` のあと別クエリで `code` を update する。`neon-http` ではトランザクションを張っていないため、2段目だけ失敗すると行は作られ `code` が null のまま(B2 と同じ見た目)で、画面には「登録に失敗しました」と出る。
- **影響**: 稀。実際に起きた記録は無い。
- **案**: `code` を DB 側の生成列/トリガーにする、または1クエリで採番する。

## ISSUE-P-007. DBエラーの文面をそのまま画面に返す
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: 未対応
- **事象(推測)**: `saveEstimate`/`deleteEstimate` の `catch` は `(e as Error).message` を画面に出す。ドライバのエラー文には SQL や制約名が含まれ得る【実際の文面は未確認】。秘密情報(接続文字列)が含まれる経路は見つかっていない。
- **案**: 画面には固定文言を出し、詳細はサーバログへ。

## ISSUE-P-008. 存在しない id の更新・削除でも成功表示/数値入力が緩い
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: 未対応
- **事象(推測)**: ① `update … where id` / `delete … where id` は対象0件でもエラーにならず、「更新/削除しました」と返る(別タブで先に削除された行を編集して保存する、など)。② 数値は `parseInt` で解釈するため `12abc` が 12 として通る。int4 を超える値は DB エラー(→P-007)。
- **案**: `returning` で件数を確認、数値は厳密にパース。入力検証を zod 等へ(CLAUDE.md 規約)。

## ISSUE-P-009. 語句検索で `%` `_` がワイルドカードとして効く
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: 未対応
- **事象(推測)**: `searchMemos` は入力をエスケープせず `%${q}%` にするため、`%` だけを入れると全件(上限20)が返る。SQL インジェクションではない(Drizzle がパラメータ化)。
- **案**: `%` `_` `\` をエスケープ。

## ISSUE-P-010. ENUM の選択肢が2か所にある
- **発見日**: 2026-10-12(コード読み) / **深刻度**: 低 / **状態**: 未対応
- **事象**: `src/db/schema.ts`(pgEnum)と `src/lib/scoring.ts`(`TYPES` など)に同じ選択肢が別々に書かれている。片方だけ変えると、画面に出るのに保存で弾かれる(または逆)。`scoring.ts` のコメント「ENUMと一致」が唯一の同期手段。
- **案**: `scoring.ts` の定数を単一の正とし、`pgEnum` をそこから作る。

## ISSUE-P-011. 用紙の既定値が「PP(特殊紙)」
- **発見日**: 2026-10-12(画面) / **深刻度**: 低 / **状態**: 未対応 / **確度**: ✅
- **事象**: 初期表示の「用紙」が「PP(特殊紙)」で、チラシの既定条件(チラシ/A4/両面4C)と組み合わせると、一般的でない用紙で類似検索が始まる。スクショ: [02-tool-result.png](screenshots/02-tool-result.png)
- **原因**: `getPapers()` が `name` 昇順で、`useState(paperNames[0])` が先頭を既定にする。登録ダイアログも同様。
- **補足**: 名前の文字列順のため、コート110 → 135 → 220 → 70 → 73 → 90 のように数字順にもならない。
- **案**: 既定用紙を明示(例: コート90)するか、並び順を用紙系統・使用頻度順にする。

## ISSUE-P-012. 認証なし×本番DB共有のリスク
- **発見日**: 2026-10-12 / **深刻度**: 中 / **状態**: 保留(SPEC §1 の仕様どおり=公開デモ)
- **事象**: 公開URLを知る誰もが登録・編集・削除できる(インライン確認のみ)。さらに**ローカルと本番が同じ Neon DB**のため、ローカルでの書込み操作は本番表示に即反映される。本WOの画面確認を読み取り中心にしたのはこのため。
