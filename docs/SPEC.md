## 1. 目的とスコープ

- 現行PoCは「合成データを埋め込んだ静的HTML」。**過去見積を登録して溜め、それを検索・流用して見積の叩き台を出す**という本来の価値を出すには、**書き込みできるDBとWebアプリ**が要る。
- 今回のスコープ(Phase 1): 過去見積の**登録・照会(一覧)・編集・削除**（フルCRUD）、語句**検索(LIKE)**、引合い条件からの**叩き台生成**(現行ロジック流用)、**確定金額の記録**、Vercelへ**公開**。
- 認証は**なし**(誰でも触れる公開デモ)。

## 3. データモデル(3テーブル・第3正規形)

**方針**: 更新が走る取引データなので **3NF** を基本にする。ただし過剰分割はしない ―
- 選択肢の列(type/size/color/data_state/reuse)は **ENUM / CHECK**(辞書テーブルにしない=コマ切れ回避。スカラなので推移的従属もなく3NF)。
- 加工の複数持ちは **`text[]`**(現代Postgresの実務。厳密1NFではないが許容。加工が自分の属性=原価/納期を持ち始めたら `finishings` へ昇格)。
- 用紙だけは `paper → paper_family` の**推移的従属**を除くため小さな辞書 **papers** に分ける(= paper_family を全行に重複させない)。

### customers(顧客)
| 列 | 型 | 説明 |
|---|---|---|
| id | serial PK | |
| name | text | 顧客名 |
| note | text (null可) | メモ |
| created_at | timestamptz | |

### papers(用紙辞書)
| 列 | 型 | 説明 |
|---|---|---|
| name | text PK | 用紙名(例: コート90) |
| family | text | 用紙系統(例: コート系)。`paper→family` の従属をここに閉じる |

### estimates(見積)
| 列 | 型 | 説明 |
|---|---|---|
| id | serial PK | |
| code | text (null可) | 表示コード。シードは E-001…、**手動登録は insert 後に `E-{id}`(3桁ゼロ埋め)を自動採番**(D39 / bugs.md B2) |
| name | text | 案件名(表示) |
| customer_id | int FK→customers (null可) | どの顧客か(S3の受け皿) |
| status | ENUM(reference/draft/confirmed/issued) | ライフサイクル |
| source | ENUM(seed/manual/tool) | 由来 |
| type | ENUM(種類) | チラシ/名刺… |
| size | ENUM(サイズ) | A4/名刺… |
| paper | text FK→papers(name) | 用紙(family は JOIN で取得) |
| color | ENUM(色) | 両面4C/特色2C… |
| qty | integer | 数量 |
| finishing | text[] | 加工(複数) |
| data_state | ENUM | 支給データの状態 |
| reuse | ENUM | 型・版・色の流用 |
| amount | integer | 見積金額(この見積の価格。スコアの単価計算にも使用) |
| cost | integer | 原価。**`source='tool'` の行の `cost=0` は「原価未入力」を表す。粗利計算には使わない**(`status='draft'` で母集団に入らないため) |
| draft_amount | integer (null可) | ツールが出した叩き台(乖離分析用)。確定金額の記録時に、サーバーが条件から再計算して保存(WO-003) |
| reason | text (null可) | 補正理由(自由記述・検索対象)。確定金額の記録時に保存(WO-003) |
| rework | text (null可) | 手戻り事由(検索対象) |
| note | text (null可) | メモ(検索対象) |
| lead_days | integer | 納期(営業日) |
| date | date (null可) | 案件日 |
| created_at / updated_at | timestamptz | |
| embedding | vector(1024) (null可) | 意味検索用(WO-023・マイグレーション 0001)。案件の文(下の §5-2「外に送るもの」)を Voyage AI で埋め込んだもの。母集団の行だけに付ける。NULL の行は意味の点 0 |
| embedding_model | text (null可) | 埋め込みを作ったモデル(`voyage-4`)。モデルを替えたとき古い埋め込みを見分けて作り直すため |

- **類似検索の母集団** = `status in ('reference','confirmed')`。
- **確定金額の記録**(WO-003): 引合い1回=新しい行を1つ insert。`status='draft'`・`source='tool'`・`amount`=確定金額・`draft_amount`=叩き台・`reason`=補正理由・引合い条件・`cost=0`(原価未入力)。母集団・一覧には入らない(`draft`)。語句検索(`reason`)には引っかかる。将来 `draft`→`confirmed` に昇格する場合は**原価の入力を必須**にする(未実装)。
- 確定金額の記録の行の `note` には、そのときの「特記・要望」の自由文を入れる(WO-023。語句検索で引ける。埋め込みは付けない)。
- **LIKE検索** = `note / rework / reason ILIKE '%語%'`(ILIKE=大小無視)。意味検索は根拠の選び方に使う(§5-2)。
- **スコアの用紙系統** = `estimates.paper → papers.family` を JOIN で取得。

### ENUM(選択肢を縛る・辞書テーブルにしない)
`type / size / color / data_state / reuse` は ENUM(または CHECK)。`finishing` の各要素はアプリ側で選択肢を制御。

### 将来の拡張(受け皿だけ用意・今は作らない=S3)
| 将来テーブル | 対応S3機能 |
|---|---|
| estimate_items(見積明細: 刷り代/組版/型代) | 見積書発行 |
| assets(型・版・色データ) | 「流用」の実体化(customer/job 紐付け) |
| inquiries(引合い) | メールからの条件抽出 |

→ estimates に `customer_id` を今入れてあるので、これらは後から**足すだけ**(既存データの作り直し不要)。

## 4. 画面とルート

実装は**別ルートを作らず、すべて `/` のクライアントコンポーネント＋モーダル**に集約した(設計時の `/estimates/new` `/estimates` 案は不採用)。

| 画面 | 内容 |
|---|---|
| `/`(本体) | 見積ツール(2026-10-19 WO-022 で並びを作り直し・D86): **上に紺の帯**(ロゴ・「見積の叩き台」/「過去見積 n件」・仮の表示・「＋ 過去見積を登録」)、**左に紺の条件パネル**(引合い条件・欄ごとの「初期値/変更」の札・**特記・要望(任意・WO-023。Voyage AI へ送る旨の注記つき)**・主ボタン・仕組みと出典)、**右に出力**(条件が変わったときの帯 → 叩き台 → 根拠 → メモ検索)。叩き台の中は「叩き台を出した条件 → 根拠が弱いときの注意 → 金額 → **判定の帯**(ネット印刷で自動で完結しない条件の5型。金額のすぐ下・記録欄より上。文言は WO-017 のまま)→ 内訳の表(刷り代=単価〔小数4桁〕×部数・組版・型・版代・合計)と確定金額の記録 → 単価の出し方と参考(たためる)」。根拠は**最大4件**で、PC は最初から開き・スマホは1行の要約にたたむ。特記を入れたときは行ごとに「条件 ◯%」「文の意味 +◯点」と「文で選ばれた」の札、意味検索が使えないときは根拠の上に1行(§5-2)。行ごとに開閉でき、最初はいちばん似た1件だけ開く。数量は1〜1,000,000の整数のみ(不正なら叩き台を出さずにエラー)。確定金額の記録は**常時表示**(叩き台がないときは無効にして理由を表示)。スマホ(760px 以下)は1列で、叩き台を作ると条件を要約にたたんで叩き台の見出しへ移り、下に固定の「確定金額を記録する」バーを出す。対象表示は条件パネルの見出しの下に「チラシ・DM・名刺・ポスター等の商業印刷」 |
| 登録/編集モーダル | `/` 上のダイアログ(PC は画面の中央・スマホは全画面)。過去見積を1件**登録**、既存を**編集**(同一フォーム、hidden `id` の有無で insert/update を分岐)。紺の見出しに「アーカイブに入る形」の見本(入力を読んで表示するだけ)。**登録・更新の成功後も閉じずメッセージ表示**(ダイアログの上に出し、上まで戻す)、新規は連続入力用にフォーム初期化(bugs.md B1)。数値欄は初期値なし・入力例は欄の外の説明・入ると全選択。流用は2択。検証はすべてサーバー側(`noValidate`。エラーはサーバーの1つの文を上に出す): 案件名必須(100文字まで)、数量1〜1,000,000、見積金額・原価は1円以上、メモ・手戻り事由は200文字まで |
| 一覧・削除モーダル | `/` 上のダイアログ(**画面の中央**。スマホは全画面)。全件**照会**(登録の新しい順)＋文字の絞り込み＋**種類のボタン**(件数つき。画面の側で数えて絞るだけ)、行の一覧(番号・案件名・仕様・手戻り・見積金額・単価・納期)の各行から**編集/削除**(削除はその場でインライン確認。「やめる」が左・「削除する」が右)。更新・削除は即 revalidate で一覧に反映 |
| 確定記録・語句検索 | 確定金額の記録は PC で叩き台の中(内訳の右)、スマホと叩き台がないときは出力の流れの中に**常時表示**(WO-009 の決まりを維持)。確定金額・補正理由は**DBに保存**し、再読み込み直後から直近10件を表示(件数つきでたためる)・確認つきで削除できる。「○ 未記録/✓ 記録済み」の札。語句検索(ILIKE・「語句の一致」)は最初はたたむ |

## 5. 計算ロジックの扱い(現行PoCの流用)

現行の以下は**変えずに移植**(決定的な計算なので `lib/` の共通TS関数にする):
- **スコアリング**(満点122点→100%正規化・種類一致必須)
- **ネット印刷で自動で完結しない条件の判定(5型。旧称「自動見積対象外の判定」)** … 言い方は出典どおりの強さにする(WO-017・D71): ① 特色=注文でき価格も出るが自動入稿は非対応・スタッフの目視チェックのみ/② 型抜き=料金表から注文できるが入稿はスタッフのチェックのみ・用紙/寸法/形状/納期に制限・**折り加工と併用すると事前見積**(折りも選ばれたときは見出しを「型抜き+折り」にし、事前見積になる旨を太字で添える)/③ 変形サイズ=商品によっては対応不可/④ サイト掲載外の特注品=個別見積(認定パートナーの紹介)/⑤ 入稿データ不備=従来どおり。判定の条件は変えていない。出典は sources.C2-b.md の各社公式一次(グラフィック/ラクスル/印刷会社)。画面に実リンク表示。② 特殊加工は 2026-10-14 から**型抜きだけ**(箔押し名刺はネット印刷の料金表から注文できるため外した。D59・D70 判断3・CHANGE-P-018)
- **叩き台**(同種の類似上位から単価中央値×数量スケール、組版=支給データ状態で加算、型版代)
- **同点の決め方**(2026-10-20 WO-023 P-9): 根拠を選ぶ点(条件の点、特記があれば+意味の点)が同じなら、**番号(id)の小さい順**。以前は DB の返す順のままで、行の更新(埋め込みの作り直しなど)で同点の並びが変わり、叩き台の金額が揺れることがあった(例: 20万部の条件で3件が72%の同点 → 今は E-001・E-002 を取り ¥510,000 に固定)
- ~~**削減効果**~~ … 2026-10-14 に画面から外した(D70 判断5・CHANGE-P-018)。時給の定数 `HOURLY`(2,610円)は組版(DTP)の加算で使うので残す
- 粗利率は金額0円の行では計算しない(「—」と表示。0除算で「NaN %」が出ていた)。叩き台の金額の計算式は変えていない

### 5-2. 意味検索(WO-023・D88・2026-10)
- **何をするか**: 左の条件パネルの「特記・要望(任意)」に文を入れたときだけ、AI の埋め込み(Voyage AI `voyage-4`)で、その文と過去案件の文の**意味の近さ**(コサイン類似度)を測り、根拠の4件の**選び方**に足す。叩き台の金額の式(単価の中央値・部数の調整・組版)と判定(`detect`)は変えない。生成 AI は使っていない(文を作らない)。
- **合わせ方**: 並べる点 = 条件の点 s(今のまま・満点122)+ 意味の点 m。この点で上位4件を選び、その後の **strong の判定(条件の点 s≥45 かつ種類一致)は条件の点のまま**。
  - 意味の点は **「その文の基準からの上乗せ」** で決める(WO-023 段3 の実測で決めた): 基準 = その文と、埋め込みのある過去案件すべての類似度の**中央値**。上乗せ = 類似度 − 基準。`m = round(MEANING_MAX × clip((上乗せ − LIFT_LO) ÷ (LIFT_HI − LIFT_LO), 0, 1))`。
  - `MEANING_MAX = 24`【仮】(122点の約2割。種類一致40点より小さく、加工16点より大きい=条件が主・文が次)。`LIFT_LO = 0.08`・`LIFT_HI = 0.25`(下の実測から)。
  - **実測(2026-10-20・voyage-4・38件・例の文16)**: 類似度は全体で 0.089〜0.638(中央 0.277)。文ごとの中央値が 0.13〜0.37 とばらつき、決まった幅(段1の仮 0.3〜0.7)では、「よろしくお願いします」のような関係のない文でも点が付く(最大 0.345)。上乗せで見ると、関係のない文4つ(急ぎ・あいさつ・天気・担当者名)は最大 0.059、関係のある文10のうち8文は一番近い案件が 0.135〜0.35(残り2文「RGBのデータで入稿される」「少部数で高品位に」は 0.08 以下で、うまく引けない)。LIFT_LO はあいさつ等の最大より少し上、LIFT_HI は関係のある文の一番近い案件の多くが満点近くになる高さ。
  - 最大の1件に必ず点を配る方式(最小〜最大で割る)は使わない(関係のない文でも満点が付くため)。中央値からの上乗せなら、関係のない文では誰にも点が付かない。どの案件も点が0なら、「入力した文に意味の近い過去案件はありませんでした」と出す。
  - 行を開くと「文の意味 +◯点/24点(近さ 0.54・この文の基準 0.24)」と、近さと基準を両方出す(なぜ点が付いたかを説明できるように)。
  - 案件の文に部数を入れたまま(P-7): 部数を抜いた文で埋め込み直して比べたところ、関係のある文10の一番近い案件は9文で同じ(違ったのは、もともと引けていない「RGB」の文だけ)で、近さの差は ±0.03 程度。数を書いた文(「3万部の大ロット」「100部だけ」)は部数ありの方が部数の近い案件を引くが、部数は条件の点で見ているので大きな差にならない。部数の近さは条件の点(数量帯)で見ているので、文からは外さなくても困らない。作り直しの手間(38件の埋め込み直し)をかけない。
  - 自由文が空なら意味の点はすべて0で API も呼ばない=**今までと同じ結果**(12通りで一致を確認。test-scenarios.md)。
  - 制約: strong は種類一致が条件なので、文で**別の種類**の案件を根拠に入れることはできない(同じ種類の中の入れ替え・上位4件への引き上げが効く範囲)。
- **画面での説明**: 根拠の行に「条件 ◯%」(条件の近さ=今の類似度)と「文の意味 +◯点」を分けて出し、条件の点だけでは上位4件に入らなかった案件に「文で選ばれた」の札。行を開くと「文の意味 +◯点/24点(近さ 0.xx)」。
- **外に(Voyage AI に)送るもの**: ①検索のとき=「特記・要望」の自由文だけ(条件の欄の値・金額は送らない)。②過去案件=案件名・種類・サイズ・用紙・色・部数・加工・支給データの状態・流用・メモ・手戻り事由を1つの文にしたもの(`src/lib/embedding.ts` の `caseText`)。**送らない**: 見積金額・原価・叩き台・補正理由・納期・日付・顧客・ID・コード。Voyage AI は「学習に使わせない(保存しない)」設定にする(代表の決定 2026-10-19。設定は代表が行う)。
- **入力の検証(サーバー)**: 自由文は文字列のみ・前後の空白を除く・**200文字まで**(`REQUEST_MAX`。認証のない公開デモから外部 API を呼べるため、長い文の送りつけを防ぐ。記録の `note` の上限 200 にそろえた)。超えたら「特記・要望は200文字以内で入力してください」。
- **失敗したとき**: キーが無い・Voyage が失敗(時間切れ 8秒【仮】・HTTP エラー)・埋め込みの列や行がまだ無いときは、例外にせず**条件の点だけ**で叩き台を出し、根拠の上に「文の意味の近さは使えませんでした(理由)。根拠は条件の近さだけで選んでいます。」と出す(止めない)。
- **埋め込みを付ける時**: 既存の行は `scripts/embed-backfill.ts`(既定は予行=外に送らない・書かない。`--write` で書く)。登録・編集のあとは Server Action が作り直す(先に NULL に戻してから付ける。失敗しても登録は成功のまま=NULL のまま、あとで backfill)。
- **記録との関係**: 確定金額の記録は、自由文もサーバーに送り、画面と同じ手順(意味の近さ → rank → buildDraft)で叩き台を再計算して保存する。画面の叩き台と違ったら(そのとき意味検索が使えなかった等)、保存はサーバーの値でメッセージに書く。

置き場所(推奨): 計算は共通TS関数、**DB問い合わせだけ Server Action**。データが小さいので負荷面はどちらでも可。

## 9. 確定した設計判断(2026-07-27)

1. **DBスキーマ** = 3NF の3テーブル(customers / papers / estimates)。カテゴリ列は ENUM、加工は text[]、用紙は papers 辞書(paper→family の従属を排除)。
2. **計算の置き場所** = 共通TS関数＋DB問い合わせは Server Action。
3. **id** = serial + 表示用 `code`。シードは E-001 を保持、**手動登録は `E-{id}` を自動採番**(D39)。削除で欠番は出るが id 一意ゆえコードも一意。
4. **シード** = 現行の合成36件を estimates(status=reference)で投入。
5. **GitHub** = 新規リポジトリで管理 → Vercel 連携。
