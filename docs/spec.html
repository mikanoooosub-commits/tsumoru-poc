Phase 1 実装済み(as-built)・本番公開済み(2026-08-11)

見積支援PoC ― Next.js版 設計

現行の静的PoC(poc/Poc.html)を、過去見積を登録して溜め、検索・流用して見積の叩き台を出すWebアプリにした。本書は実装に合わせた as-built。作成 2026-07-27 / 最終更新 2026-08-10

1. 目的とスコープ

現行は「合成データを埋め込んだ静的HTML」で、登録・保存ができない。本来の価値(過去データの再利用)を出すため、書き込みできるDB＋Webアプリにする。今回(Phase 1)は 登録・照会(一覧)・編集・削除(フルCRUD)・語句検索(LIKE)・叩き台生成・確定金額の記録・公開まで。認証なし(公開デモ)。

2. 技術構成

層採用理由
フレームワークNext.js(App Router)UIとサーバ処理を1つに
DBNeon(サーバーレス Postgres)Supabaseの無料枠を使わない。将来 pgvector で意味検索へ拡張可
DBアクセスDrizzle ORM型安全・Neon/Turso両対応。SQL文字列を手書きしない
ホスティングVercelGitHub連携で git push→自動デプロイ

認証なし公開デモ
セキュリティ: Neon の接続文字列はサーバ側のみ(環境変数)。ブラウザから直接DBに繋がず、Server Action / Route Handler 経由にする。

3. データモデル(3テーブル・第3正規形)

方針: 更新の走る取引データなので 3NF。ただし過剰分割しない ― カテゴリ列(type/size/color/data_state/reuse)は ENUM(辞書テーブル化しない=スカラで従属もなく3NF)、加工は text[]、用紙だけ paper→paper_family の推移的従属を除くため papers 辞書に分離。

customers(顧客)

列型説明
idserial PK
nametext顧客名
notetext(null可)メモ
created_attimestamptz

papers(用紙辞書)

列型説明
nametext PK用紙名(例: コート90)
familytext用紙系統(例: コート系)。paper→family の従属をここに閉じる

estimates(見積)

列型説明
idserial PK
codetext(null可)表示コード。シードは E-001…、手動登録は insert 後に E-{id} を自動採番(D39 / B2)
nametext案件名(表示)
customer_idint FK→customers(null可)どの顧客か(S3の受け皿)
statusENUMreference / draft / confirmed / issued
sourceENUMseed / manual / tool
typeENUM種類(チラシ/名刺…)
sizeENUMサイズ(A4/名刺…)
papertext FK→papers(name)用紙(family は JOIN)
colorENUM色(両面4C/特色2C…)
qtyinteger数量
finishingtext[]加工(複数)
data_stateENUM支給データの状態
reuseENUM型・版・色の流用
amountinteger見積金額(価格・スコアの単価計算に使用)
costinteger原価
draft_amountinteger(null可)ツールの叩き台(乖離分析用)
reasontext(null可)補正理由(検索対象)
reworktext(null可)手戻り事由(検索対象)
notetext(null可)メモ(検索対象)
lead_daysinteger納期(営業日)
datedate(null可)案件日
created_at / updated_attimestamptz
(将来) embeddingvector(N)意味検索用・Phase 2

類似検索の母集団 = status in ('reference','confirmed') ／ LIKE = note・rework・reason ILIKE ／ 用紙系統 = paper→papers.family を JOIN。将来 embedding 列で意味検索。

将来の拡張(受け皿だけ・今は作らない=S3)

将来テーブル対応S3機能
estimate_items(見積明細: 刷り代/組版/型代)見積書発行
assets(型・版・色データ)「流用」の実体化(customer/job 紐付け)
inquiries(引合い)メールからの条件抽出

estimates に customer_id を今入れてあるので、これらは後から足すだけ(既存データの作り直し不要)。

4. 画面(すべて / 上のモーダル)

実装は別ルートを作らず、すべて / のクライアントコンポーネント＋モーダルに集約した(設計時の /estimates/new /estimates 案は不採用)。

画面内容
/(本体)見積ツール: 引合い条件 → 判定(ネット印刷で自動で完結しない条件の5型。2026-10-14 に言い方を変更)・叩き台・類似案件・手戻り注意・削減効果
登録/編集モーダル過去見積を1件登録、既存を編集(同一フォーム、hidden id の有無で insert/update 分岐)。成功後も閉じずメッセージ表示、新規は連続入力用にフォーム初期化(B1)
一覧・削除モーダル全件照会＋絞り込み、各行から編集/削除(削除はインライン確認)。更新・削除は即 revalidate で一覧反映
確定記録・語句検索/ の常時表示の帯(WO-009。折りたたみは廃止)。確定金額・補正理由はDBに保存し、再読み込み直後から直近10件を表示。語句検索は Neon へ ILIKE

現行の見せ方(初期は入力カードのみ→ボタンで結果表示、記録/検索はトグル内)は踏襲。

5. 現行PoCから流用するロジック

  • スコアリング(満点122点→100%正規化・種類一致必須)
  • ネット印刷で自動で完結しない条件の判定(5型。旧称: 自動見積対象外の判定) … 出典は各社公式一次(sources.C2-b.md)。画面に実リンク
  • 叩き台(同種の類似上位から単価中央値×数量スケール、組版=支給データ状態で加算、型版代)
  • 削減効果(時給2,610円=全印工連 令和7年度・30分→15分。2026-10-14 に 2,631円から変更)

これらは決定的な計算なので lib/ の共通TS関数にし、DB問い合わせだけ Server Action に置く(推奨)。

7. デプロイの流れ(Phase 1)

  1. GitHub に新規リポジトリ作成 → Next.js を push
  2. Vercel で GitHub リポジトリを import(以後 git push で自動デプロイ)
  3. Neon でDB作成 → 接続文字列を Vercel の環境変数に(サーバ限定)
  4. Drizzle でマイグレーション(テーブル作成)→ 36件シード投入
  5. 公開URL発行

8. やらないこと(S3本体・原則を飛ばさない)

  • 認証 / 見積書PDF発行 / メール自動返信 / MIS連携 … S3本体なので今回は作らない
  • 冊子のページ数・固定費(版代/型代)の計算モデル化 … 適用範囲外
  • 意味検索 … Phase 2 へ(今回はLIKEまで)

9. 確定した設計判断(2026-07-27)

  • ① DBスキーマ = 3NF の3テーブル(customers / papers / estimates)。カテゴリ列は ENUM、加工は text[]、用紙は papers 辞書(paper→family の従属を排除)
  • ② 計算の置き場所 = 共通TS関数＋DB問い合わせは Server Action
  • ③ id = serial + 表示用 code。シードは E-001 を保持、手動登録は E-{id} を自動採番(D39)。削除で欠番は出るが id 一意ゆえコードも一意
  • ④ シード = 現行の合成36件を estimates(status=reference)で投入
  • ⑤ GitHub = 新規リポジトリ → Vercel 連携
